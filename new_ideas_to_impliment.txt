This is a planning pass only. No game behaviour will be changed until this

CURRENT PROJECT STATE
---------------------

1. The 2D game already loads every .csv file in maps/game/ from its menu.
2. The ray-cast game currently always loads maps/game/raycaster.csv.
3. Both modes already share rules/objects.csv, the maps, and most artwork.
4. Object ID 15 and the complete 2D collapsing-floor feature already exist.
5. The 2D game has delta-time movement, animated lava and torches, animated
   rock demons, a darkness overlay, and a small permanent player light.
6. Fire and water demons each currently use one static image.
7. The duck changes image by direction but has no timed walk/idle animation.
8. The existing launcher starts the ray-cast game as a separate process, so it
   cannot currently pass the selected level to it or receive its win/death
   result cleanly.


DESIGN PRINCIPLES
-----------------

- A level remains one CSV file that can be opened in either mode.
- Object IDs and gameplay meaning remain centralized in rules/objects.csv.
- Mode-specific drawing stays separate from shared gameplay rules.
- New timers use elapsed seconds, not frame counts.
- Features will be delivered in small phases and tested before the next phase.
- Existing maps remain playable while new mechanics are introduced.

PHASE 2: ONE-WAY GATE
---------------------

Goal: add a map object that the duck may cross in exactly one allowed direction.

1. Reserve four object IDs in rules/objects.csv, one for each allowed direction:
   one_way_up, one_way_down, one_way_left, and one_way_right. Four IDs make the
   direction visible in the map editor and avoid hiding map-specific direction
   data in Python.
2. Add one gate base asset and rotate/flip it at load time for the four variants,
   unless four hand-drawn directional assets look clearer.
3. Add a small shared direction/collision helper that checks the player's old
   position, requested movement, and gate rectangle/cell. The player may enter
   only while moving in the arrow's allowed direction.
4. In 2D, resolve the forbidden side like a barrier without trapping a player
   who is already overlapping the tile.
5. In ray-cast mode, use the same direction rule in can_stand()/move_player().
   Render the gate as a billboard or thin transparent gate so the permitted
   route remains visually understandable.
6. Decide explicitly whether demons obey gates; the recommended first version
   applies gates only to the player.
7. Add each gate direction to the map editor automatically through objects.csv.

Acceptance checks:
- Each of the four variants permits crossing only in its configured direction.
- Approaching diagonally cannot bypass the gate.
- Turning around while overlapping does not trap or teleport the player.
- Behaviour matches in 2D and ray-cast modes.

Recommended rule for clarity:

- Torch raised: glowing markings reveal it as a passage; it becomes traversable.
- Demons always treat it as a wall so their routes remain predictable.

   inside cannot embed the duck in a wall.

   pass through and a translucent billboard/edge marker indicates the opening.

- Lowering the torch inside never traps or kills the player.
- Rays and physical collision agree in first-person mode.
- Enemy pathing remains stable when the state changes.
